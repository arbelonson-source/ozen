# Ozen for Android

Status: approved by the owner on 2026-10-10 ("just start building the app");
stage 1 started and finished the same day, and stage 2 is under way. See
[Where it stands](#where-it-stands).

## What the owner asked for

- Android at the same priority as the iPhone app, to reach Android's much
  larger number of users. Ozen is global: twelve caption and interface
  languages, not only Hebrew.
- Phone hardware varies far more on Android, so checking which phones can do
  what is a core part of the work, not an afterthought.
- Built as a full Kotlin rewrite (approach B), chosen over sharing the Swift
  core.
- Tested on the owner's Android phone and on Waydroid on the Linux PC.

## Assumptions (the owner can correct these)

- Same features as the iPhone app: live captions with speaker names, name and
  sound alerts, History with search, quick replies, the home computer and the
  cloud services, in the same twelve languages, right-to-left where needed.
- Free and open source under the same AGPL-3.0 licence, no ads, no accounts,
  no telemetry. Network only for features the person turns on (the home
  computer, the cloud services, model downloads).
- Released as a free APK on GitHub. Releases happen only when the owner
  says so. Not on Google Play: opening a developer account there needs
  identity documents, which is ruled out.

## Where it lives

An `android/` folder in this repository, so the docs, the home server, the
issue tracker and the shared test cases stay in one place. Two Gradle
modules:

- `android/core`: plain Kotlin with no Android dependency, the counterpart of
  `Sources/OzenKit`: caption cleanup and line layout, sentence cutting,
  speaker clustering, alerts and their quiet hours, History and search,
  the home-computer protocol, the cloud services, settings and their
  lenient decoding. Its tests run on the PC's JVM in seconds, with no
  emulator.
- `android/app`: everything that needs Android: the microphone, the speech
  engines, the background service, notifications, the screens.

## Keeping two apps in step

The main risk of a rewrite is the two apps slowly behaving differently.
Behaviour that both must share is written down once as test cases in
`Tests/Fixtures/` (JSON files: an input and the expected output), and both the
Swift tests and the Kotlin tests read the same files. A fix to one app starts
by adding a case there, which then fails in the other app until it is fixed
too. The cloud services' sample answers (`Tests/Fixtures/cloud/`) are the first
such files. Over the port, the cases grow to cover caption cleanup, number
emphasis, name matching, line layout, pluralisation and settings decoding.

## Listening

- Microphone: `AudioRecord` at 16 kHz mono from the speech-recognition source,
  run inside a foreground service of type microphone, so captions continue
  with the screen off and the phone in a pocket, with the ongoing
  notification Android requires (it shows the newest line, like the iPhone's
  lock screen).
- On the phone: whisper.cpp through a small JNI layer, running the same
  ivrit.ai Turbo and Ozen a3 Hebrew models converted to whisper.cpp's format,
  and Whisper's general models for the other languages. The model size is
  picked by the phone check below.
- The model files (made 2026-10-10 with whisper.cpp v1.9.5's own converter
  and quantize tool, from the same weights as the iPhone's): Ozen a3, the
  iPhone's recommended model, is 1,625 MB at 16 bits, 874 MB at q8_0 and
  574 MB at q5_0. On ivrit.ai's WhatsApp test set (the 36 shortest of its
  54 voice messages, 20 minutes; greedy decoding, no earlier text, on a PC
  processor) the three got 10.5%, 10.7% and 10.6% of words wrong, so
  compressing to q5_0 costs nothing measurable and the phone downloads q5_0.
  Where it downloads from is the owner's call: the iPhone's models are
  releases of `ozen-models`.
- whisper.cpp's processor code is built once per processor level (seven for
  64-bit ARM, ARMv8.0 to v9.2; fourteen for x86_64) and the app loads the
  best one the processor reports, so a phone from about 2018 on gets the
  dot-product and half-precision instructions the compressed models lean on,
  and an older one still runs.
- Telling a voice from a pot or a tap uses the same detector as the iPhone,
  Silero VAD (MIT), but in whisper.cpp's own copy (an 864 KB file shipped in
  the app) instead of Apple's model format. The iPhone scores each 0.26 s
  of sound as its eight Silero steps combined (the chance any of them heard
  a voice); the phone does the same. Measured on this PC on 2026-10-10
  against the reference Silero: 52 s of Hebrew speech came out voiced in
  75.5% of chunks against 75.0%, with 99.5% of chunks agreeing, and a
  minute each of kitchen, living-room and washing-machine noise had no
  voiced chunk in either. whisper.cpp leaves Silero's memory unset when
  it loads, which made hiss sound like a voice on the emulator, so the app
  clears it first.
- Android's own recogniser (`SpeechRecognizer`, on-device where the phone has
  it) as the counterpart of Apple's, with the same rule: never a silent
  fallback to sending audio to Google.
- The home computer over the same WebSocket protocol as the iPhone, and the
  cloud services from `docs/design/2026-10-10-cloud-services.md`.

## The phone check

Run on first start and again from Settings, in about half a minute, with
nothing sent anywhere:

1. Reads the processor type (the on-phone model needs 64-bit ARM), the number
   of cores, memory, free storage and the Android version.
2. Records two seconds to confirm the microphone delivers sound.
3. Transcribes a short clip shipped with the app with the smallest model and
   times it, then tries the next size up only if the first was comfortably
   faster than real time.
4. Picks the largest model that keeps up, or, on a phone too weak or too full
   for any, explains in plain words that captions will come from the home
   computer or a cloud service, and offers to set one up.

The result shows in Diagnostics and can be copied by hand, which is how
results reach the compatibility table; the app itself reports nothing.

## The compatibility lab

- The owner's phone over USB (`adb`), for real speed, microphone and
  battery behaviour.
- Waydroid on the Linux PC for the screens, the flows and the twelve
  languages. It runs on the PC's processor, so it says nothing about phone
  speed.
- For cheap, old and popular phones nobody here owns: Google's Firebase Test
  Lab, which runs the phone check as an automated test on real devices and
  has a free daily allowance. It needs a Google account, which is the owner's
  call.
- The results go in `docs/android-compatibility.md`: phone, Android version,
  memory, the model it can run and how fast, with the date tested.

Phone makers that stop background apps (Samsung, Xiaomi, Huawei, OnePlus) get
step-by-step instructions inside the app, shown when captions are stopped in
the background, as the iPhone app does for its own background limits.

## Stages

Each stage ends with its tests green on CI and a LEDGER entry; the owner sees
it working on the phone after stages 2, 3 and 4.

1. Core: `android/core` with the shared test cases and a JVM test job on CI.
2. Listening: microphone, background service, whisper.cpp, Android's
   recogniser, the home computer and the cloud services, shown first as plain
   text on a bare screen.
3. Screens: the caption screen, Settings, History, alerts, onboarding, in all
   twelve languages, with TalkBack and font scaling checked.
4. The phone check and the compatibility lab, with the first table rows.
5. Release, when the owner says so: an APK on GitHub.

## Where it stands

As of the evening of 11 October 2026:

- Stage 1 is done. `android/core` holds 115 Kotlin files, almost all
  ported from OzenKit: caption cleanup, layout and number emphasis, speaker
  clustering, alerts and quiet hours, History and its day headings,
  conversation statistics, settings, the home-computer protocol, the cloud
  services, and `CaptionPipeline` itself with its recovery and failure
  paths. 1,476 tests run on the JVM, and 164 more cover the app module; CI's
  Android job runs them on every push and keeps a debug APK of each commit.
- Stage 2 has started:
  - whisper.cpp runs on the phone through the JNI layer, one pass at a time,
    with the iPhone's rules for trying a pass again when it looks wrong
    (WhisperKit's thresholds, ported as `WhisperFallbackPasses`). On the
    emulator, a 52-second Hebrew recording run through the whole phone
    engine with Ozen a3 at q5_0 came out with 8% of its words wrong.
  - On the iPhone, a speech model nothing holds any more is freed by
    itself; on Android it has to be closed by hand. A model the pipeline
    lets go of is now closed explicitly instead of staying in memory.
  - whisper.cpp always works through a full 30-second window, however
    short the sound, so a live pass took about 33 seconds on the emulator.
    Live passes now cover only the sound they carry plus a second, and take
    about 3 seconds there. Finished lines keep the full window: on the PC,
    on ivrit.ai's WhatsApp clips cut into 8-second pieces, the shorter
    window got 13.9% of words wrong against 11.2% for the full one, and
    still 13.5% with 5 seconds to spare. Live text is replaced when its line
    is finished, so its few extra mistakes don't stay on screen.
  - A finished line still takes about 30 seconds on the emulator, and during
    continuous speech the sound that piles up meanwhile makes the next pass
    a finished line too, so live text shows only now and then. How fast a
    real phone is, the emulator can't say; that waits for a phone over USB.
  - The pipeline's microphone source lists the built-in, wired, USB,
    Bluetooth and hearing-aid microphones, and notices when a phone call
    silences the recording (Android keeps recording zeros through a call).
    If captions fail or are stopped during the call, its end is still
    noticed, by the phone leaving call mode, so they come back by
    themselves as on the iPhone.
    Its device tests pass on the emulator.
  - The listening service runs the caption pipeline with the engine the
    settings choose: the home computer, the phone's own model from a file
    already on the phone, or a cloud service. Cloud keys are kept on the
    phone like the iPhone's, one sealed file per service, and entered in
    Settings. The status button and the notification say
    what the pipeline is doing, from listening to paused for a call. A
    fresh install, with no model file and nowhere yet to download one
    from, says the language model isn't on the phone yet, and accepting a
    pairing link from the home computer starts captions there.
  - Pausing or stopping captions stops the phone model's pass instead of
    letting it run to its end with its result thrown away (about 30
    seconds on the emulator). whisper.cpp only checked its stop request
    between stages, so Ozen builds it with a small patch
    (`android/app/src/main/cpp/whisper-abort.patch`) that lets the encoder
    stop partway too. A closed caption session, a model whose loading or
    warm-up was stopped, and a stopped model when the phone says memory
    is short are all given back instead of staying loaded.
  - Device tests run the whole path, a recorded 52-second lecture in
    place of the microphone through to the lines on the screen, and check
    live text on 20 seconds of the lecture with its pauses cut out.
- Stage 3 has started:

    bold text, bold numbers, unsure marks, the screen staying on and the

## Testing

- `android/core`: every OzenKit test that covers shared behaviour gets a
  Kotlin counterpart, plus the shared fixture cases.
- `android/app`: instrumented tests on an emulator and Waydroid for the
  service, permissions and screens; the phone check as an instrumented test
  for Firebase Test Lab.
- CI: a Linux job builds the APK and runs the JVM tests on every push, beside
  the existing iPhone jobs.

## Setting up this PC

Java 21, the Android SDK command-line tools, the NDK for whisper.cpp and the
Gradle wrapper inside `android/`; Waydroid if it is not already installed.
Java 21, the SDK (platform 36, build tools 37) and the Gradle wrapper were set
up on 2026-10-10, and the NDK (30.0) followed the same day for whisper.cpp,
with an Android 16 emulator (x86_64) for the device tests. Waydroid is not
installed yet.

## Risks

- Speed: Turbo-size models may be too slow on mid-range phones; smaller models
  are worse at Hebrew. The phone check and the lab measure this before any
  promise is made.
- Background limits differ by phone maker; covered by the instructions and by
  testing on the lab's phones.
- Since Android 11, an app may start listening in the background only while
  it is on screen, so captions have to be started from the app itself; the
  in-app explanation of this is written at stage 3.
- Drift between the apps; covered by the shared test cases.

## Not in the first version

Android Auto, watches, tablets' split-screen layouts, and a lock-screen widget
beyond the ongoing notification.
